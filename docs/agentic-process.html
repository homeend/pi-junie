Open Mercato skills · Cezar · applied to pi-junie

An agent-driven process for building the pi-junie harness

What Open Mercato does (podcast, skills repo, Cezar), which parts fit this project, and a proposed process that starts in Claude Code and ends with Pi doing the work. Analysis and design only: nothing was installed or changed.

1. Summary

  • The reusable part is the process shape, plus about a dozen skills. Open Mercato runs a spec-driven pipeline: requirements → spec with questions → review by a second model → agent implementation in a worktree with a safety net → review → human test → human merge. That shape fits pi-junie almost unchanged.
  • The fully automated chain does not fit your local-only wish as shipped. The om-auto-* skills keep their state in a tracker (issues, PRs, labels) and push to origin. The one chain that stops before a PR is bound to Claude as host. No skill merges locally.
  • Cezar fits. It runs locally without GitHub, queues tasks, gives each a git worktree, has a diff review gate, and can pick a different agent per workflow step. It already has a Pi runner, marked experimental.
  • Decided (23 Nov): the process is local. Work starts with Claude Code dispatched through gg, Cezar is started locally to queue and oversee tasks, the second review is done by Pi with a model you choose, and Pi becomes an executor later. The local-capable om-* skills cover spec, audit, review and validation; backlog and specs are files in the repo; merge is by hand on your OK.
  • Pi can do the second review without a new plugin. A review skill plus the model picker covers one reviewer; your own agent-cross-review skill plus the subagents pi-junie already has covers several models. Plugins exist but none is needed to start (section 7).
  • What we would write ourselves is small: an AGENTS.md, a config file, one spec overlay, one Cezar workflow file and two short project skills (section 9).
  • JetBrains AI can now pay for unattended Pi (23 Nov update). The repo gained packages/jetbrains-ai, a Pi provider that signs in to JetBrains AI from the command line and in headless runs. Standalone Pi no longer needs separate provider keys, so the second review can become a queued Cezar step (section 7).
  • The ground is prepared: the repo now also lives on the Linux file system at ~/others/pi-junie, with clean line endings and the tests passing there (section 8, phase 0).

Source: the YouTube auto-transcription of Better Software Design 105, uncorrected. Timestamps mark the minute where the statement starts. Tool and model names are often garbled in the transcript, so repo names are used where the two disagree.

Where the detail is. You expected the skills and development flow in the last third. The process is actually in the middle: flow 0:14–0:19, specs 0:33–0:36 and 0:47–0:49, skills 0:37–0:45, Cezar 0:52–0:59. The last third covers merge review, dynamic context and evals 1:07–1:24.

How skills make the process

  • Why skills exist. Five or six people prompted by hand, each differently. A hackathon produced 300 PRs in a weekend, all different, some untested. Skills made every run apply the same rules and the same labels 0:40.
  • Skills are “machines in a factory”, fitted to the project's workflow, not general methodology 0:39. Together they act as a project manager for agents 0:28: stages a task passes through, with loops 0:45.
  • A setup skill detects the stack and standards and writes one config file. Every other skill reads it 0:38. In the repo this is om-setup-agent-pipeline and .ai/agentic.config.json.
  • State lives in GitHub. Issues, PRs and labels are the coordination layer: an agent marks a PR in progress, and writes a handoff into the PR so work can resume after a token limit 0:42.
  • Specs are the agent's input context, 200–500 lines (unit not stated), with summary, architecture and user stories. Large work gets a parent document plus one spec per phase. Finished specs are archived, never edited; a change gets a new spec 0:34 0:36 0:47.
  • Context is kept small. A short AGENTS.md; a classifier skill that loads only the skills matching the task; and build-time facts per module extracted from the AST as JSON, which alone made a cheap model work well 1:17 1:19. They optimise for weak models because that also helps strong ones 0:12.
  • Skills are improved from real sessions. A share-session skill sends a cleaned session back; failures are turned into about 200 evals that every targeted model must pass 1:20 1:22.

Cezar in their day-to-day

  • A management cockpit: pick a defined step (for example issue to PR), the task goes to a queue, and a runner such as Claude Code starts when resources allow 0:53.
  • Load 100 tasks on a small server and close the laptop. It throttles on available memory and uses a git worktree per task 0:54 0:57.
  • Two-layer dispatch: a strong model plans and scans, a cheap one does the individual reviews 0:55.
  • What it adds beyond skills: a queue, scheduling, a record of what was delegated, and model routing. Before it, they opened ten terminal windows and forgot them 0:56.

Their advice

  • Start from an opinionated architecture; the core team's main job is architecture and context 0:07.
  • Speed deceives; a composed process with loops and verification is needed on top of single sessions 0:31.
  • Bottlenecks are understanding and control of the system, and testing 1:25.

3. The skills repo

Checked in t:\others\skills: 74 skills, each a directory with a SKILL.md in the standard Agent Skills format. All skill frontmatter was read; about 11 skill bodies were read closely and the rest are classified from their descriptions.

  • They are project-neutral. A lint rule bans Open Mercato references inside the skills. A few are shaped for a platform product and noted below.
  • No skill calls GitHub directly. Skills name tracker operations, and a descriptor file (.ai/trackers/<tracker>.md) implements them. Shipped descriptors: github, gitlab, forgejo, jira, linear. There is no local one.
  • Install: npx skills add open-mercato/skills. A project can override part of a skill with a file at .ai/skills/<skill>/SKILL.md without forking it.
  • Name suffixes: auto- means autonomous and non-interactive; -loop is a long-run engine with checkpoints; -multi adds multi-model review; -optimized hands bounded work to cheaper models.

4. Cezar

Checked in t:\others\cezar by reading docs and code. Start-up and the review path were run later; see section 11.

What it isA Node CLI plus a local web cockpit on 127.0.0.1:4321. It starts agent CLIs you are already logged in to, one git worktree per task (.ai/cezar/worktrees/<id>, branch cez/<id>), and streams progress, tokens and cost. MIT licence. No database: state is files in .ai/cezar/ and ~/.cezar/.

Dispatch starts with gg, which you already use; Cezar takes over the queue once it runs locally (phase 2 in section 8). At any one time, one of them dispatches.

5. The central trade-off

Three of your wishes pull against each other: adopt as much as possible, keep work local, and end on Pi. The shipped automation assumes a forge, and the one stop-before-PR chain assumes Claude.

Stages 4 and 5 as a Cezar workflow. It uses the syntax from Cezar's reference; a sketch, not yet tried. Pi's findings arrive with the diff at the review gate, and you decide whether to send the task back:

# .ai/cezar/workflows/feature-from-spec.yaml
name: feature-from-spec
steps:
  - id: implement
    name: Implement
    prompt: "Implement the spec at {{task}}. Write the replay test first."
    runner: claude              # later: pi
  - id: verify
    name: Tests and types
    command: "npm test && npm run check"
    onFail: { retry: implement, max: 2 }
  - id: review
    name: First review
    prompt: "Review the diff against the spec at {{task}}. Fix real issues only."
    skill: om-code-review
    runner: claude
  - id: verify-again
    name: Tests after review
    command: "npm test && npm run check"
    onFail: { retry: review, max: 1 }
  - id: second-review
    name: Second review by Pi
    prompt: "Review the diff against the spec at {{task}}. Report findings. Do not edit files."
    skill: om-code-review
    runner: pi                  # the second review is Pi's
    model: provider/model       # the reviewer model you choose

Getting a task's build into AIR (stage 6)

AIR starts <repo>/bin/pi-air from the main checkout, but at stage 6 the change exists only in the task worktree. The launcher finds its root from its own location, so a worktree's bin/pi-air runs that worktree's code and writes its own log (.pi-dev/pi-air.log inside the worktree).

  • A second agent entry in ~/.jetbrains/acp.json, for example pi-junie-dev, pointing at a fixed link such as ~/pi-junie-under-test/bin/pi-air. The link is switched to the worktree under test; the stable pi-junie entry keeps running main.
  • The worktree needs its dependencies: scripts/dev.sh worktree as the first step of the workflow. Cezar does not run worktree scripts from a git-tracked config.json.
  • One build under test at a time. Implementation runs in parallel, testing in AIR is serial: you switch the link (the test-handoff skill prints the command and the checklist), start a new chat with pi-junie-dev, and send back or accept.

Settings that follow from your standing rules

  • No merge into main without your OK: review gate on (CEZ_REVIEW_GATE=1), tasks not autonomous, worktree mode and not Cezar's trunk mode (which commits in place), and merge as an explicit step by you.
  • The branch is merge-ready before you are asked: with parallel tasks main will have moved, so syncing main into the branch and re-running the gate happens in the task worktree every time, never in the main checkout.
  • Nothing pushed without you: no publish option on om-check-and-commit, no GitHub automations in Cezar.
  • Recordings contain keys: acp-examples/ stays git-ignored, so it is absent from task worktrees. Agents work from the redacted fixtures in test/fixtures; a new fixture is extracted in the main checkout before the task starts.

7. The second review, done by Pi

The first review is the implementer's side: Claude reviews its own change with om-code-review and fixes what it finds (om-implement-feature has this built in). The second review is Pi on another model. That is the cross-vendor review from the podcast, and it exercises pi-junie on real work.

What Pi needs before it can review

From reading the bridge and the two review skills, no bridge code is missing. Four things have to be in place:

  • The review skills in the project's .agents/skills. The bridge runs Pi with its own state folder, so skills installed for Claude Code (~/.claude/skills) or for your personal Pi are not seen. It does load the opened project's skills and offers them as commands.
  • The pipeline config. om-code-review starts by loading .ai/agentic.config.json and a tracker descriptor, and runs the setup skill itself when they are missing. Run om-setup-agent-pipeline once beforehand, so a review does not turn into a setup session.
  • The task's worktree as the working folder. The skill runs the validation commands on the checkout it is in. Run from the main checkout, it would test main, not the branch.
  • A reviewer that reports and does not edit. om-code-review returns findings with a verdict. The second review stays report-only so that two agents never change the same branch.

Which credentials Pi uses: JetBrains AI in both cases

A model call needs someone to pay for it. Since the 23 November update of the repo, JetBrains AI can be that someone whoever starts Pi.

Pi is started byHow model calls are paidJetBrains AI?
AIR (pi-junie)AIR gives the agent a local proxy address and a proxy key. AIR adds your JetBrains AI token upstream. Pi never holds a credential.Yes
Cezar, gg or a terminal (standalone Pi)The jetbrains-ai provider in packages/jetbrains-ai, loaded with -e or pi install. It calls JetBrains' model service directly, as the Junie CLI does.Yes, with the new package

The package is a copy of pi-extension-jetbrains-ai 1.0.0 from the junie-pi repository, so it is maintained elsewhere and nothing had to be written here. It offers two ways to sign in:

  • Browser login: /login → JetBrains, once, in an interactive Pi. Pi stores the credential in its auth.json and refreshes it, so later headless runs on the same machine reuse it. Pi and the browser must be on the same machine.
  • Junie API key: JUNIE_API_KEY in the environment (from junie.jetbrains.com/cli). No interactive step at all, which suits Cezar steps. The environment key wins over a saved browser login.

Headless use:

cd <task worktree>
JUNIE_API_KEY=... pi --print -e ~/others/pi-junie/packages/jetbrains-ai \
   --provider jetbrains-ai --model <model> "<task>"

This is the same call shape JetBrains' own eval uses for Pi (docs/eval-parity-plan.md, section 1).

What I checked here: Pi 1.5.2 from the repo's node_modules starts headless with the extension and accepts the jetbrains-ai provider. With a JUNIE_API_KEY read from ~/.config/pi-junie/env (outside the repo, readable only by you), one small headless request each to gpt-6-luna, claude-opus-5-5 and gpt-6.1-sol returned an answer. Without a key Pi stops with "No API key found for jetbrains-ai".

Two limits to know:

  • Standalone Pi is not pi-junie. Headless Pi with this extension is plain Pi: no bridge, so none of the bridge's permissions, Junie compatibility or Default model group. Subagents and other plugins are available only if installed into that Pi. A headless entry point for pi-junie itself is step 6 of the eval plan and is not built yet.
  • The package uses Junie's client identity, not its own registered JetBrains application (its README says so). That is a question for the Junie team before wider use, not for local work.

Consequence for the process: the earlier choice between "reviews stay in AIR" and "a second bill for provider keys" is gone. Phase 1 can still review in AIR because you are present; from phase 2 the review is a Cezar step with runner: pi, paid by JetBrains AI. The same holds for Pi as an executor in phase 3.

Starting Cezar locally

Cezar oversees only the tasks it starts itself; it does not watch gg's workers. So it is started in phase 1 and given one of the pilot items, next to gg.

scripts/dev.sh setup                    # installs Cezar 0.20.0 into .dev-tools/, nothing global
CEZ_DRY_RUN=1 scripts/dev.sh cezar      # tour with mock agents, spends nothing
scripts/dev.sh cezar projects add .     # once: register the repository
scripts/dev.sh cezar                    # cockpit on http://127.0.0.1:4321

scripts/dev.sh cezar switches the review gate on, switches Cezar's telemetry and skill auto-update off, and points Cezar's Pi runner at scripts/pi-jbai. The committed .ai/cezar/config.json sets:

  • defaultRunner: "claude" for now.
  • skillsRepos: the Open Mercato skills at the same commit as skills-lock.json.
  • requiredChecks: npm run check and npm test.
  • The workflow's first step prepares the task worktree: scripts/dev.sh worktree (dependencies and skill links).

It is a long-running process, so it belongs in its own named tmux session. The parallel cap (maxParallel, default 2) is in ~/.cezar/config.json.
