pi-junie

Pi, the open coding agent, runs in-process as an ACP v1 agent of JetBrains AIR. A bridge translates between AIR's protocol and Pi's SDK; Junie's behavior (models, Default group, Eco, cost savings, configuration, changed-file reports) is added around it as Pi plugins. Pi itself is never modified.

Inside the bridge packages/bridge/src

acp/

Everything ACP-shaped: JSON-RPC peer, v1 wire types, the codec (pure translation to and from core types), method dispatch, the changed-files report.

Never imports Pi.

core/

Neutral types and the ports between the two sides: AgentBackend, BackendSession, turn events, permission and question asks.

Imports nothing but itself.

pi/

backend.ts plus one module per concern: catalog, discovery, ingrazzio, mixes, plugins, tools, transcript, phases, session-store, subagents, todo, plan-mode, web-access, ask-user, safe-commands, junie-compat, proxy-auth, stream-errors, failures.

Never imports ACP.

compat/

AIR capability strings mapped to plugin requirements: what to advertise in initialize, and why a feature AIR wants is missing.

Standalone.

The boundaries are enforced by test/architecture.test.ts, so the protocol and the agent can change independently.

The life of a prompt

  1. initializeThe client says who it is and which AIR features it takes. The bridge answers with its capabilities and _meta.jetbrains.air.capabilities (subagent sessions, changed-file reports).
  2. providers/setAIR hands over its LLM proxy routes. The bridge discovers each route's models, keeps those Junie's picker offers, loads the account's feature flags (Default group, Eco implementation model) and Junie Lite.
  3. session/newA chat on the recommended Default level, or JUNIE_MODEL. The answer carries config options: mode, model with the Default group, effort, Eco, Brave Mode. A welcome message lists the plugins.
  4. session/promptA Pi AgentSession is created or resumed from its transcript, with the bridge's extensions, the built-in and detected plugins, the IDE's MCP tools and the project's skills.
  5. The agent loopPi streams text, thoughts and tool calls. The bridge turns them into session/updates: message chunks split into commentary and answer, tool rows with diffs and live terminal output, plans, subagent child sessions, usage_update with the chat's cost.
  6. PermissionsEvery tool call passes the bridge's gate: read-only tools run, others ask through session/request_permission unless Brave Mode or a safe-command rule allows them. Questions and plan reviews use AIR's forms.
  7. End of the turnIf AIR asked, the files the turn's edits changed go out as agentFileChangeReport; then the prompt result with token usage. A failed turn becomes AIR's typed failure row.

Models

Where they come from

  • AIR's proxy (default): one slot per vendor, bound by providers/set; a placeholder key that proxy-auth.ts strips, AIR adds the real credentials.
  • Ingrazzio route: feature flags (JUNIE_MIXES, ECO_MODE_IMPLEMENTATION) and Junie Lite, free.
  • Junie keys: JUNIE_API_KEY adds the JetBrains AI group; JUNIE_<VENDOR>_API_KEY binds a slot to the vendor's API. AIR's own binding replaces a key binding.
  • Custom profiles: Junie's JSON files, each its own provider, custom:<profile>.

Default group and Eco

  • Default group: Junie's levels (Lite, Normal, Hard, Frontier) from the account flag, each a model and an effort; a new chat starts on the recommended one.
  • Eco (Junie's Model Mix): a virtual model eco/<slot>/<model>. The chosen model explores read-only and reports a plan (create_plan, report_plan), then GPT-6 Luna at high implements it.
  • The router decides each request from its own conversation, because all chats share one model runtime.
  • Eco is remembered per model; a Default level carries its own; it needs Junie Cost.

State on disk

~/.pi/pi-junie/ (the bridge's own)

  • sessions/<id>.json: chat metadata (model, effort, level, Eco, cost, title)
  • sessions/pi/*.jsonl: Pi transcripts, the source of history replay, cost and /stats
  • auth.json, models-store.json: isolated from your own Pi logins
  • eco.json: Eco choice per model; subagents/: child transcripts

Elsewhere

  • ~/.pi/agent/: your terminal Pi: installed plugins and their on/off switches (read by the bridge)
  • ~/.junie/models/: Junie's custom model profiles; ~/.junie/logs/: prompt usage log
  • .pi-dev/pi-air.log: the bridge's log, every ACP and HTTP exchange, secrets redacted

Testing

All tests run offline: a fake LLM proxy speaks the vendor listings and Anthropic's streaming format (including a broken stream), a memory wire stands in for AIR, and fixtures extracted from real Junie ↔ AIR recordings are replayed against the bridge. Live checks happen by hand in AIR after each commit.
